# 麦麦开袋台 · 本地原型

给多人团餐组织者使用：把订单整理成应收清单，人工点数后看差额，再逐人记录餐是否已领走。

现已增加共享点餐：成员用同局域网电脑、平板或手机选择单品，系统组合套餐与单品并官方核价，点餐员确认并到官方支付页付款，官方回查确认已付后把餐品和逐人归属带进开袋台。

## 共享点餐启动

仍只使用 Node.js 标准库，没有额外依赖。真实模式：

```sh
node prototype/group-server.mjs --token-file token.txt --host 0.0.0.0 --port 45075
```

合成演示模式（不连接麦当劳，不收费）：

```sh
node prototype/group-server.mjs --demo --host 0.0.0.0 --port 45076
```

终端显示组织者地址、本机管理口令及可选局域网地址。点餐员在运行服务的电脑上打开 `http://127.0.0.1:端口/group.html`，输入该口令；只有回环连接加正确口令才能进行下单、支付查询和清点操作。不要把管理口令发给成员，分享的是餐桌邀请链接。

Windows 已安装 Node.js 时可运行本目录的 `启动共享点餐.cmd` 或 `启动合成演示.cmd`。把源码解压到自己选择的目录；启动器会切换到自身目录，真实模式读取上一级由你自行准备的 `token.txt`。仓库不携带凭据。

**成员设备要与运行服务的电脑处于可互通的局域网。电脑、平板和手机都可使用，有线与无线均可，不限定同一个 Wi-Fi 名称。** 邀请链接在成员浏览器中打开即可。WSL NAT 地址不一定能被其他设备访问，优先在 Windows 原生 Node 下运行上述入口。若系统防火墙阻止入站，需由电脑所有者决定是否允许该 Node 进程在专用网络访问；本项目没有自动改防火墙、开公网端口或部署隧道。Windows 原生启动及跨设备连通尚未完成实机验收。

邀请使用同一局域网的 HTTP，适合可信网络上的原型试用，不作为公网部署方式。MCP Token始终在服务端，成员只能修改自己的意愿。服务端不开放任何任意工具调用接口。

## 从意愿到开袋

1. 点餐员选择“外带自取”或“麦乐送到家”。外带可选择收藏餐厅或附近地标；麦乐送读取已有地址后直接选择可配送餐厅。成员加入后按汉堡/主食、小吃、饮料、甜品、其他筛选，也可搜索名称。
2. 成员只选单品和份数，切分类保留已选清单；提交空清单表示本次不点餐，截止前可以修改。
3. 全部已加入成员提交后，点餐员截止收集并计算买法。系统生成套餐配置和单品组合，再逐个官方整单核价；保留纯单品基线，额外餐品单独列明。
4. 页面按**本轮成功核价的候选金额**排序，不把有界搜索或菜单展示价称为全菜单全局最低。具体搜索范围、遗漏详情和候选数量会显示。
5. 外带优先选择官方返回的外带方式；麦乐送展示配送费和收货地址。点餐员核对人员、餐品、额外内容、金额及收货方式，勾选确认后创建待支付订单。创建前重新核价并核对配送地址，变化则要求再次确认。
6. 打开服务端返回的 HTTPS 官方支付链接，本人付款。点击“我已付款，核对状态”后，服务端用已保存的订单号回查；客户端按钮本身不代表已付款。
7. 官方订单已支付且商品匹配后，仅生成一份开袋清单。逐人意愿保留，多余餐品进入应收总量但不默认分给某个人；点餐员可再添加领餐人分配。
8. 创建超时或结果未知不会自动重试。先在官方订单核对，再按页面提示关联本次订单号。已知订单待支付、已取消或餐品不匹配时，不会自动入账。

餐桌和开袋记录保存在项目 `.omo/bagdesk-rooms/`（演示为 `.omo/bagdesk-demo/`），不是公开静态目录。MCP Token、支付链接、手机号、地址和取餐凭证不写入餐桌记录；成员口令只保存哈希。重启后支付链接不保留，可在官方 App 继续付款，然后重新核对状态。

浏览器里的组织者口令通常只在内存；进入同源开袋台时通过一次性 sessionStorage 交接，读取后删除。成员身份保存在本标签页 sessionStorage。已支付清单的点数和领取动作会保存到本机服务；纯本地合成样例和手工导入仍仅保留当前页面内存。

## 餐厅地图与官方图片

真实餐厅卡片显示官方店名、地址、营业状态和已返回的营业时间。地图按钮按店名、地址和城市打开高德地图搜索，供核对同名门店；不把零坐标或未经确认的坐标画成精确落点。

单品卡使用官方菜单或同一规格详情返回的图片。只允许 HTTPS 官方图片域名，加载时不附加MCP凭据和页面引用信息；缺图或加载失败显示明确文字，仍可按名称选餐。

GPS自动定位属于可选服务，需要点餐员在本机配置高德 Web 服务 Key。真实Key只放环境变量或项目 `.env`，不提交Git、不打包、不传浏览器；仓库只保留 `.env.example` 的空值示例。其他开源部署者使用自己的Key。配置 `.env` 后可通过 `node --env-file=.env prototype/group-server.mjs --token-file token.txt --port 45077` 启动。

`.gitignore` 排除了 `.env` 和私有Token，实际交付包也应按文件白名单构建；忽略规则不能清除已提交过的秘密。若Key曾进入公开历史，应在服务商控制台撤销并重新申请。本原型没有保存或提交真实地图Key。

浏览器定位仅在用户主动点击后申请权限；没有配置服务时不采集坐标，仍可使用收藏门店、地标和配送地址。局域网普通HTTP上的浏览器可能不允许定位，点餐员在服务电脑的localhost页面操作，或在正式部署时配置HTTPS。

GPS结果及麦乐送真实核价尚未完成真实验收；使用时分别需要自己的高德Key和账户已有配送地址。实现与合成测试不替代这两项真实验证。可先体验真实外带菜单、官方图片和地图核对入口。

## 启动

需要 Node.js 22 或更高版本，不安装依赖。在本项目根目录执行：

```sh
node prototype/server.mjs
```

终端会显示 `BAGDESK_READY http://127.0.0.1:端口`，在浏览器打开该地址。服务仅监听本机地址，只提供原型的网页和代码文件，不开放项目其他文件。停止服务使用终端 Ctrl+C。

## 先走一次十二人演示

演示全部为人工合成数据，不是用户的真实订单。共12人、36件餐品：12个汉堡、12份薯条、8杯可乐和4杯红茶。

1. 开始开袋，按清点结果逐项确认数量。未点数保持“未点数”，不会默认为0。
2. 用“演示少一份”载入人工设置的短缺情境，观察薯条差额；这不是系统自动看见了餐袋。
3. 给同事逐人递餐。剩余不足时不能递出，已领取者不能重复领取。
4. 退回某份餐，或用撤销恢复上一步；如果已经发出餐品，实收不能改成低于已发数量。
5. 恢复样例后重新尝试完整点数和十二人领取。

## 导入自己的订单 JSON

手工导入模式只在当前页面处理 JSON，不主动连接麦当劳账户。也可导入 `query-order` 返回中的商品部分：

```json
{
  "data": {
    "orderProductList": [
      {
        "productName": "双人分享套餐（合成示例）",
        "quantity": 2,
        "comboItemList": [
          { "itemName": "汉堡", "itemQuantity": 2 },
          { "itemName": "薯条", "itemQuantity": 2 },
          { "itemName": "可乐", "itemQuantity": 2 },
          { "itemName": "不要冰", "itemQuantity": 1 }
        ]
      }
    ]
  }
}
```

也接受直接含 `orderProductList` 的对象。导入后逐行确认：

- 子项数量是“每份套餐”还是“整行合计”。上例选每份会把餐品各算4件，选整行合计则各算2件。
- 每个子项是实际餐品还是特调说明。例如“不要冰”是否忽略，由人确认；程序不根据名称猜。
- 缺失、非整数或异常数量会报错，不会补成0。

导入只保留商品名、数量及子项信息，丢弃订单号、地址、电话、取餐凭证等其他字段。生成清单后没有自动人员归属；可以只做验收，也可以手动添加领餐人和需要的餐品。

## 数据与状态

- 应收、实收、已领取是不同数量。未点数、少件、超收和收齐分别显示。
- 接口定义未充分说明父套餐与子项的数量倍数，首版要求人工选择口径。
- 子项可能包含特调，不能把所有子项都当作额外食物。
- 手工导入的输入和操作仅保存在当前页面内存，刷新会清空；共享点餐产生的已支付清单则由本机服务保存。不要把真实订单或凭据发到公开仓库。
- 不使用照片识别、不自动判断餐厅漏装、不联系客服或补单。真实下单只在共享点餐流程中经点餐员明确确认进行，支付由本人在官方页面操作。
